# 앱 특성 차원 (요구 쪽)

- 작성일: 2026-10-01
- 상태: 초안, 검토 중

## 0. 이 문서의 역할

판정은 **앱의 요구**와 **구성 요소의 능력**을 맞춰 보는 일이다.

```
앱 특성 프로필 (이 문서의 차원들, 코드에서 추출)
        ×
구성 요소 능력 표 (DB, 캐시, 큐, 스토리지, 컴퓨트 플랫폼 … 공식 문서에서)
        ↓
불일치 = 요구 > 능력  → 요구를 만족하는 가장 싼 구성 요소로 교체
과잉   = 능력 ≫ 요구  → 더 싼 구성 요소로 축소
코드 변경 = (현재 구성 요소 → 새 구성 요소)의 차이에서 나옴
```

상황을 나열하지 않는다. 상황은 차원 값과 능력의 조합에서 나온다. 그래서 차원은 **유한하고 서로 겹치지 않아야** 하며, 각 차원은 "코드에서 어떻게 읽어내는가"를 가져야 한다.

### 근거의 세 종류

SQLite 예시에서 보듯, 차원 값을 정하는 근거는 세 종류다. 차원마다 세 종류를 모두 찾는다.

| 종류 | 뜻 | 예 (쓰기 동시성) |
|---|---|---|
| **기술** | 무엇을 쓰는가 | `better-sqlite3`, Prisma `provider = "sqlite"` |
| **사용 맥락** | 그걸 어떻게, 누가, 얼마나 쓰는가 | 역할·결재·부서 테이블, 쓰기 API 수, 워커 프로세스 수 |
| **고통 흔적** | 이미 한계에 부딪힌 흔적 | `database is locked` 처리, `busy_timeout`, 재시도 루프, 관련 이슈·커밋 메시지 |

기술만 보면 "SQLite를 쓴다"까지만 알 수 있다. 사용 맥락이 요구의 크기를 정하고, 고통 흔적은 요구가 능력을 이미 넘었다는 가장 강한 증거다.

코드에 근거가 없으면 도메인 기본값으로 **가정**하고 드러낸다(설계 문서 원칙 3).

## 2. 이 틀로 판별되는지 확인

### 2.1 SQLite 업무 시스템 (기준 예시)

| 단계 | 내용 |
|---|---|
| 추출 | C1 쓰기 동시성 = 높음 (근거: 결재·부서 테이블, 쓰기 API 다수, `gunicorn -w 4`, `database is locked` 재시도 코드) / D1 = 고정(내부) / D2 = 중간 이상 / F1 = 짧아야 함 / B2 = SQLite 파일 |
| 능력 | SQLite: 한 순간에 쓰기 하나, 같은 호스트의 프로세스만 공유(WAL), 매니지드 HA 없음 ⚠️근거없음 |
| 불일치 | C1 > SQLite 쓰기 능력, F1(인스턴스 이중화) > SQLite 공유 능력 |
| 선택 | 요구를 만족하는 가장 싼 후보 = 매니지드 PostgreSQL |
| 코드 변경 | SQLite → PostgreSQL 차이: 드라이버, SQL 문법, 타입 엄격성, 동기/비동기 API, 직렬화가 사라지면서 드러나는 경쟁 조건(C2가 "있음"이면 잠금 처방이 함께 나옴), 데이터 이전 |

D1이 "고정(내부)"이어도 D2와 C1이 높으므로 교체가 나온다. 예전 설계(사내 도구 → 트래픽 L0 → SQLite 유지)가 틀린 결론을 낸 이유는 D2와 C1을 따로 보지 않았기 때문이다.

### 2.2 같은 틀로 나오는 다른 경우 (상황 목록 없이)

| 경우 | 걸리는 차원 | 불일치하는 능력 |
|---|---|---|
| 세션을 메모리에 둔 앱을 2대로 늘림 | B1 있음 | 인스턴스 간 상태 공유 불가 |
| Cloud Run에서 웹소켓 채팅 | A3 장시간 연결 | 요청 타임아웃(최대 60분) ⚠️근거없음 |
| Vercel에서 10분짜리 엑셀 생성 | A2 수 분 | 함수 최대 실행 시간 ⚠️근거없음 |
| Cloud Run 요청 기반 과금에서 응답 후 메일 발송 | A4 있음 | 요청 밖 CPU 미할당 ⚠️근거없음 |
| 사내 도구인데 EKS 3개 존 + NAT | D1 고정, D2 낮음, F1 길어도 됨 | 능력 ≫ 요구 → 과잉, 축소 |
| 쇼핑몰 재고를 Firestore로 차감 | C2 있음, C3 강한 불변식 | 저장소의 트랜잭션·경합 처리 방식 확인 필요 |

## 3. 다음에 필요한 것

1. **구성 요소 능력 표**: DB(SQLite, PostgreSQL, MySQL, Firestore, DynamoDB, Supabase …), 캐시, 큐, 오브젝트 스토리지, 컴퓨트 플랫폼(티어 0·1·2)별로 위 "맞춰 볼 능력" 항목을 공식 문서 근거로 채운다. 기존 878개 카탈로그가 재료다.
2. **추출 방법 상세**: 차원마다 언어·프레임워크별 탐지 패턴과 LLM이 판단할 부분을 나눈다.
3. **교체 차이 표**: 자주 일어나는 교체(SQLite → PostgreSQL, 메모리 세션 → Redis, 로컬 디스크 → 오브젝트 스토리지, 서버리스 함수 → 컨테이너)마다 코드 변경 항목. 교체 쌍은 능력 표에서 나오므로 이것도 유한하다.
4. **설계 문서 갱신**: 시나리오 × 수준(D/T/U/C)은 이 차원들에서 파생되는 요약으로 바뀐다. 예: 트래픽 폭증 수준 = D3, 재난 수준 = F1·F2·F3.
